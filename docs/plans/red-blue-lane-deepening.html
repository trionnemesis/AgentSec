The constraint that shapes everything below

One contract binds the two lanes. Splitting the skill would break the binding.

Two lanes, one skill — never two skills.

Issue #60 (merged as PR #61) already settled the product question: do not split the purple workbench into independent red-team and blue-team skills. The asset that makes AgentSec different is a single Attack–Detection Contract that binds, in one reviewed YAML file, all four axes at once — (1) what reproducible stimulus the red side sends, (2) how prevention must block it, (3) what signal the blue side must see and by when, and (4) whether the event can be reconstructed and answered afterwards.

Fork the skill and each half degrades into "generate attacks only" or "check the SIEM only" — precisely the red_only shape the validator already treats as an error, because a prevention-only scenario cannot tell a real fix from a silent bypass. So this plan deepens each lane where it already lives. It never separates them.

What "update" means for each lane

Sharpen both halves — held together by the contract in the middle

The list under each lane is the operating guidance to deepen (a progressive-disclosure reference the skill loads on demand). Neither lane can produce a runnable scenario or a verdict on its own.

Red lane · phase 2

Reproducible attack + prevention

Send a fixed, reviewed stimulus and pin the control that must hold the line.

  • Read the target schema, including supported_operations. Batch preflight stops on any unsupported_driver_operation before any approval is consumed or the target is contacted.
  • Prefer executor: replay for PR gates: fixed text means a changed verdict is a changed system. Never enable the parked PyRIT/pytest executors — they resolve to NotImplementedExecutor by design.
  • Pair prevention must_not: tool_call with must: policy_decision … deny. A lone must_not passes for an agent that merely happened not to call the tool.
  • Need pre-cleanup state? Schedule snapshot_state during the attack — replay cleans up in a finally block, and a cleanup failure fails closed.
  • Approvals are minted by a human out-of-band. No tool mints one, and there is no autonomous red-team planning.

Blue lane · phase 3

Evidence + detection timing

Prove whether the defence would have noticed — and noticed in time.

  • Four distinct boundaries: attack timeout, telemetry settle, detection SLA (within_seconds on must_fire) and response SLA. Polling makes a late signal visible; it does not make it timely.
  • Live Wazuh / OTel / tool-audit must correlate to the canonical agentsec.run_id. Missing, conflicting or foreign-run correlation is error — never a gap, never secure.
  • every_tool_call_audited is per invocation: prefer tool_call_id/span_id; each audit record is consumed once, so two same-named calls can't be satisfied by one record.
  • Backend outage, a pagination failure, a missing required source, or undecidable correlation are all pipeline error — never downgraded to a detection or evidence gap.
  • Keep response: not_tested honest until a real runbook or automation exists. Do not fill it in for coverage.

Guardrails — what this plan must not become

These carry over verbatim from issue #60 and the roadmap's "deliberately not planned" row. A follow-up agent that crosses one of these has left the plan.

  • No independent red / blue skills. The lanes stay bound by one contract.
  • No autonomous attack generation, no LLM judge, no PyRIT/pytest executor, no fifth axis, no multi-agent scenarios yet.
  • Do not widen PurpleVerdict, the four-axis precedence, the schemas, the executor registry, or the MCP capability surface.
  • The skill is guidance, not a boundary. A new safety invariant belongs in the service, schema, permissions, hooks or tests — named in the PR — or it is advisory only.
  • Do not start #14 beyond the credential-free static profile. Skill Assurance stays deferred.
Done means done

Acceptance & stop condition

Shipped against this brief

  • The red and blue lanes each have a deepened, self-contained reference, and SKILL.md routes to them (PR #65).
  • The skill_eval static profile runs in its own CI gate and checks the skill's frontmatter, references and digests (PR #65).
  • AGT-CONFIG-005 ties ASI-TOOL-PERMISSION-BYPASS to .claude/settings.json, making it verifiable (PR #84).
  • make check, agentsec validate --strict and the MCP contract tests stayed green; no product surface widened.

What remains — and the stop condition

Two roadmap-named Track B gaps, each a small reviewable PR: tag AGT-XPIA-001 at a memory surface, and record fixtures + Wazuh rule packs for 100901–100905 and the four bundled rules. Then stop.

Do not drift into: live Wazuh/OTel end-to-end · the async run worker · external catalogue packaging · the full Skill Assurance runner. Those have their own backlog.
