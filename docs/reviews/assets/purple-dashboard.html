Code review

Twelve findings, all twelve fixed

Ranked by how badly each one undermines the project's own central claim: that an untested or uncollectable axis must never round up to a pass. All twelve are now fixed with regression tests; two of them — 07 and part of 08 — by correcting a claim rather than the code, and each says so. The bundled corpus still returns the same four verdicts and the same exit 1.

Severity
01 A target that names its tool-call span differently gets a free pass on the evidence axis evaluation/axes.py:28,455 · correctness fixed
FixedThe span name and tool-name attribute now come from attack.config, and the check returns error — never pass — when no span matches or matching spans carry no tool name. agentsec validate gains a tool_audit_without_spans warning for contracts that assert the check while collecting no OTel evidence. Verified against a doctored fixture: secure/evidence pass → error/evidence error, and declaring the convention makes it grade normally again.

TOOL_CALL_SPAN = "agent.tool_call" is hardcoded, and its own comment says targets using another convention "set it in the scenario's attack.config" — but nothing reads that. attack.config is consulted in exactly one place, execution/promptfoo.py:56.

_unaudited_tool_calls returns traced − audited. When no span matches the hardcoded name, traced is empty, the difference is empty, and every_tool_call_audited reports pass. The cross-referencing of two independent sources — the thing that makes this axis worth having — silently stops, and the axis goes green.

Suggested fixRead the span name from attack.config (or from the target), and when every_tool_call_audited is asserted while zero spans match the configured name, return error rather than pass.
02 The report is stamped with a profile it never filtered on service/harness.py:676 · store/sqlite.py:148 · correctness fixed
FixedResultStore.list_runs takes a profile and generate_report passes it. The parameter is now optional everywhere: omit it and the report covers every profile and says "all", rather than claiming one the caller never chose.

generate_report takes a profile argument, passes it to normalize_batch as the report's label, and never passes it to list_runs — which has no profile parameter at all. So agentsec report --profile pr renders a report headed "profile pr" over whatever runs exist, nightly included.

The reusable CI gate calls exactly this, and docs/deployment.md suggests pointing AGENTSEC_DB at a CI cache — which is the configuration where a mislabelled report stops being cosmetic.

Suggested fixAdd profile to ResultStore.list_runs and filter on it, or drop the parameter from the report label.
03 The report counts every historical run; the coverage resource counts only the latest reporting/normalizer.py:127 · store/sqlite.py:285 · correctness fixed
FixedNew latest_per_scenario() keeps the most recent summary per (scenario, target), breaking created_at ties on run_id — a whole batch shares a timestamp to the second, so the tiebreak is load-bearing. The repro below now reports 4 runs, 2 secure, 2 blocking with no duplicates, and agrees with verdict_counts. A new superseded_runs field keeps the JSON honest that history exists.

verdict_counts deliberately dedupes to the latest run per scenario, with a comment explaining why: "counting every historical run would let a scenario that failed fifty times last month dominate today's picture." normalize_batch does no such thing.

Reproduced during this review: running the same four scenarios twice, then agentsec report, produced secure: 4, blocking_count: 4, and a blocking_scenarios list naming AGT-TENANT-001 and AGT-MEMPOIS-001 twice each. The HTML dashboard and agentsec://coverage now disagree about one database.

Suggested fixRoll up the latest run per (scenario, target) for the headline counts, and show history as an explicit trend rather than as today's totals.
04 The axis rollup is computed and then never rendered reporting/normalizer.py:133 · templates/report.html.j2 · dashboard gap fixed
FixedThe shipped report now renders axis_counts as a segmented bar per axis, each segment labelled in text and carrying a shape glyph so status never rests on colour alone. Verdict and severity filters drive the table and the detail cards together, with an empty state; verdict_history() supplies the per-scenario trend the rollup drops, drawn as a sparkline with the latest run outlined. --warn moved off #b26a00, which sat below the normal-vision separation floor against --fail. Still one self-contained file with no external assets.

normalize_batch builds axis_counts — pass / fail / not_tested / error for each of the four axes — and the HTML template renders verdict cards, a table and collapsible detail, but never touches it. The four-axis contract is the product's central idea and the one metric the dashboard omits.

There is also no filtering, no sorting and no trend, while the roadmap describes a "metrics dashboard". The band at the top of this page is the missing view, built from the same JSON.

Suggested fixRender axis_counts as a segmented bar per axis; add verdict/severity filters and a per-scenario verdict history.
05 Extra MCP tool arguments are silently dropped, not refused mcp/server.py:151-201 · claim vs behaviour fixed
FixedThe advertised schema is now the declared schema — required, pattern and additionalProperties: false all reach the wire — and the derived argument model sets extra="forbid", so an unknown key is refused rather than discarded. The same call now returns isError: true with extra_forbidden at 'url'. The refusal lands in the client's error rather than the audit log, which is the accepted cost of not patching FastMCP's dispatch path.

The README states that tool schemas "reject url, sql, command, path, token and friends, with additionalProperties: false". Verified against a real stdio client, they do not.

call  agentsec_preview_run {target_id:"demo-agent-fixture",
                            url:"http://attacker.example/x"}
→     {"ok": true, ...}          no error · no audit row

tools/list advertises, for all 11 tools:
      required = []   additionalProperties = <unset>

The generated callable in _make_tool_callable carries a synthesized signature containing only declared properties, so FastMCP drops unknown keys before validate_arguments — the one place that holds the real schema — ever sees them. Not exploitable: the argument has no effect. But the audited-refusal property the project leans on, and that .claude/hooks/guard_agentsec.py exists to reinforce, does not hold at this boundary.

What does hold, confirmed: required, pattern, enum, maxItems and read-only mode were all enforced server-side.

Suggested fixGive the generated callable a **kwargs tail so unknown keys reach validate_arguments and are refused and audited rather than discarded.
06 Evidence-backend URLs bypass the private-address guard policy/allowlist.py:80 · evidence/wazuh.py:92 · security fixed
Fixed_check_endpoint now walks every evidence backend URL as well as the adapter's, and new assert_private_url() re-asserts the rule inside all four collectors at the moment of dialling — closing the hole left by treating unresolvable names as private at load time.

_check_endpoint inspects target.adapter.base_url and only when adapter.kind == "http". target.evidence.wazuh.url and the OTel endpoint are never checked — so a public Wazuh Indexer URL in policy/targets.yaml is accepted, and WAZUH_INDEXER_USER / WAZUH_INDEXER_PASSWORD are sent to it over httpx.BasicAuth. The README's "endpoints must be private" reads as covering all of them.

Related: _is_private_host treats an unresolvable name as private, with a comment that "the run itself will fail loudly if it is not" — nothing re-checks at run time, so a name that does not resolve at config load and resolves publicly at run time is never caught.

Suggested fixRun every configured backend URL through _check_endpoint, and re-assert the private-address check at collection time rather than only at load.
07 start_run does not require the prior preview it documents mcp/contract.py:167 · service/harness.py:284 · doc vs behaviour fixed
FixedCorrected in the documentation rather than the code, deliberately. Enforcing a preview only on the gateway would create the "Claude-only code path" that harness.py's own docstring forbids, and enforcing it everywhere would break the CLI and CI, neither of which previews. The tool description and both READMEs now call it a convention and point at what is enforced: the approval token.

The tool description says "Requires a prior preview" and the README says "agentsec_start_run requires it". HarnessService.start_run records no preview state and enforces nothing — a first call runs immediately.

Suggested fixEither record a short-lived preview marker per (target, profile) and require it, or reword both the tool description and the README to "always preview first" as advice.
08 Confirmed for issue #7: read-only mode still advertises all eleven tools mcp/server.py:107 · confirms an open issue fixed
Fixedbuild_server() skips every read_only=False tool when AGENTSEC_MCP_READ_ONLY=1. tools/list drops from 11 to 8 — execution is absent, not denied. That closes acceptance criterion 1 of issue #7; resource allowlisting and evidence redaction stay open there.

Issue #7 lists "a real stdio MCP client smoke test verifies capability listing" as an unmet acceptance criterion. Done, and it confirms the report: with AGENTSEC_MCP_READ_ONLY=1, tools/list returns all 11 tools including agentsec_start_run, agentsec_promote_finding and agentsec_generate_report, and resources/list is unfiltered. Dispatch refusal works; capability discovery is unchanged.

Worth noting for deployment option C: because agentsec_generate_report is read_only=False, the read-only "report gateway" is the one process that cannot generate a report.

Suggested fixTrack under issue #7 — no separate work item.
09 Quarantine expiry silently reinterprets a non-UTC timestamp policy/guard.py:102 · correctness fixed
Fixedif until.tzinfo is None: until = until.replace(tzinfo=UTC) — an offset that was written down is now converted rather than overwritten.

datetime.fromisoformat(quarantined_until).replace(tzinfo=UTC) overwrites an existing offset instead of converting it. 2026-08-01T00:00:00+08:00 becomes 2026-08-01T00:00:00Z, and the quarantine runs eight hours longer than the author wrote.

Suggested fixif until.tzinfo is None: until = until.replace(tzinfo=UTC).
10 must_fire has no lower time bound evaluation/matchers.py:118 · robustness fixed
Fixedmatch_alert rejects ts < window_start too. Still unreachable through the shipped collectors, which is exactly why the guarantee now lives in the matcher rather than in whichever collector supplies the alerts.

match_alert rejects an alert only when ts > deadline. An alert that fired before window_start still satisfies a must_fire. Not reachable today — the OpenSearch collector bounds gte at query time and fixtures are rebased into the window — but the guarantee lives in the collector, not the matcher, so a new collector loses it silently.

Suggested fixReject ts < window_start in match_alert too.
11 Run-id minting races, and a collision overwrites the earlier run service/harness.py:796 · store/sqlite.py:115 · robustness fixed
FixedNew run_counter table and next_run_id(): one INSERT … ON CONFLICT … RETURNING, so two processes on one workspace cannot be handed the same id. Also removes the limit=1000 scan that doubled as a ceiling on runs per day.

_next_run_id reads list_runs(limit=1000), computes max + 1 in Python, and save_run is ON CONFLICT(run_id) DO UPDATE. Two processes sharing a workspace mint the same id and the second silently overwrites the first — losing a run without a trace, in the tool whose job is to be the record. The limit=1000 scan is also a ceiling on runs per day.

Suggested fixMint the id inside the insert transaction, or use a INSERT-only path so a collision raises instead of overwriting.
12 The guard hook over-matches, and the README's first command is blocked by it .claude/hooks/guard_agentsec.py:30,84 · README §2 · developer experience fixed
FixedMarkers are matched against host-shaped tokens rather than the raw command, and the exemption is scoped to the same token and anchored to a whole label — so ordinary commands are allowed again while prod.customer.com --proxy localhost and example.com.evil.net are both refused. 20 cases pinned in tests/test_guard_hook.py. Both READMEs note the blocked quick-start command, and the gate workflow passes inputs through env:.

Production markers are matched as bare substrings anywhere in the command. Hit organically during this review: grep -rn "Live Artifact" docs/ was refused because "live" appears in the name of the project's own documented feature.

More importantly, the exemption at line 84 tests the whole command, so any command mentioning localhost anywhere exempts every marker in it — curl https://prod.customer.com --proxy localhost passes the check.

Separately: agentsec run is denied by both .claude/settings.json and the hook, deliberately and correctly — but §2 of the README tells a new user to run exactly that, with no note that inside Claude Code the route is agentsec_start_run.

Suggested fixMatch markers against the parsed host rather than the raw string, scope the exemption to the same token as the marker, and add one line to README §2.
